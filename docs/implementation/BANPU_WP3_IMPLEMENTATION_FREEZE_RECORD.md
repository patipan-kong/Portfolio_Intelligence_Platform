## F. Aggregate implementation-corpus identity and manifest convention

### F.1 Convention (existing, not invented)

Two existing conventions govern, and both are applied as recorded:

**Hashing.** Canonical identity is **Git-canonical LF content** — SHA-256 over
file bytes with trailing `\r` stripped from every line — the convention defined
and adopted in [`BANPU_WP1_FREEZE_IDENTITY_CORRECTION_RECORD.md`](BANPU_WP1_FREEZE_IDENTITY_CORRECTION_RECORD.md)
§4 and made binding for future verification by its §9. That record adopted this
convention precisely because "the raw working-tree byte count is a function of
the platform/editor checkout state (CRLF vs LF), not of file content." Under
`core.autocrlf=true` on this branch, four of the nine corpus files currently
carry CRLF in the working tree; raw hashing would bind an identity that a
different checkout could not reproduce. Raw values are recorded alongside in §E
for completeness but are **not** the canonical identity.

**Manifest.** For each corpus row, in §E table order (production rows 1–4, then
test rows 5–9), the line `<repo-relative-path><TAB><SHA-256 uppercase hex><TAB><canonical byte count>`;
lines joined by `\n`, with one trailing `\n`; the whole manifest encoded UTF-8;
then SHA-256. This is the algorithm reconstructed and byte-verified against a
recorded value in WP1 Freeze Identity Correction Record §6, and it is the same
`path<TAB>SHA256<TAB>bytes<LF>` form stated in BANPU-WP2 Implementation Freeze
Record §3. The identical algorithm reproduces the governing planning corpus
identity in §B exactly, which independently validates its application here.
